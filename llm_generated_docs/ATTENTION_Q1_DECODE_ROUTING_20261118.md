# RK3588 长上下文单 token GQA 的路径选择

Qwen3-4B 在 4K 上下文的常规 decode 中，prefill 优化前后均约 7.80 tok/s。单独增加 M4 指数查表后，整模型 4K / 16K 吞吐分别提升 0.58% / 2.17%。16K 每步节省 4.72 ms，同时多耗费 3.17 个 CPU 核毫秒。

提交 `2043c24` 优化了 causal、每组 4 个 query head、每段 32 个 query 行的 prefill。在 Qwen3-4B 的普通自回归 decode，每层生成一个位置，每个 KV head 上的四个独立 query head 打包成物理 M4。运行时追加一个 K/V，再执行 Q1。末尾 query 能看到所有已写入的 token，算子将这一次调用转换为 NO_MASK 并走单块串行路径。默认 LUT 可用时，NPU 做 QK，CPU 求每行真实最大值并中心化，DPU 算指数，NPU 做 PV，CPU 归一化。V 幅值和任务数保护仍可切到原有 CPU softmax。生成首 token 前的 prompt 会受益于 prefill 优化；后续每步没有进入 M128 快路径。[Rust 层追加与运行](../src/npu/attention.rs) · [图选择、M128 门槛及 Q1 入口](../native/rk_npu_matmul/src/rk_npu_attention_f16.cpp)

## 连续 decode 的整模型复测

第一批全模型对照以相同伪随机 token（种子 42）预装 3968 个位置，再做 128 次带 LM head 的单 token forward，按旧库、2043c24、M4 查表、M4 查表、2043c24、旧库顺序各启一个进程，每个进程先预热，再独立计时。六次依次得到 8.273、8.394、8.465、7.039、7.203、8.315 tok/s。反向轮次与板上其他 Rust 编译重叠，本组仅留作诊断，不以六个数的均值估计收益。[原始进程记录](evidence/gqa_q1_routing_20261118/model/summary.json)

第二批使用同一个 Rust 驱动、同一份连续 WikiText token 和同一 Qwen3-4B W4A8 模型，切换三个独立进程加载的 native 动态库。4K 覆盖末尾 128 步（索引 3968–4095），16K 为 16256–16383。每种长度先做 128 步 Q1 预热；完成第一遍后截断 KV 并重放，同一进程测两遍，表中取两遍总时长的平均，再折算吞吐。只计每次完整 forward，包括 LM head；复制和导出 logits、prefill、采样与恢复 KV 在计时外。16K 使用实际各位置的 RoPE、Q/K/V 和全模型逐层计算。运行时配置上限 32768，实际预留 16384，三版相同。首次 16K KV 预留在上限 16384 的域布局下失败，驱动报告 32 MiB IOVA 映射失败；使用现有 32K 容量规划后完成预留。

| 4096 | 主线 ec363d9 | 7.799 | 128.22 | 38.59 | 29.59 |

M4 原型相对主线的吞吐变化为 +0.58% / +2.17%（4K / 16K），Attention 区间耗时变化为 -1.97% / -3.54%。每种长度的 128 × 151,936 = 19,447,808 个 FP32 logits，均在两遍和所比版本间逐位相同且全部有限。同一版本的两遍来自一个模型进程，16K 每种版本只启动一个进程；不同进程的整模型差异仍可能包含线性层耗时波动。采样器以约一秒为间隔记录仍存活进程的 CPU 时间；在十个正式窗口内观察到的编译进程 CPU 核秒合计 0.00。在本次 32K 配置容量下，三种动态库使用同一份冻结的线性层策略缓存，加载命中和缺失分别为 100、34，缺项使用内置策略。4K 首批合成输入的 4160 容量与此处的域划分不同，绝对 tok/s 不跨批次比较。窗口数据与每步墙钟、CPU 时间均已保存。[全模型逐步结果](evidence/gqa_q1_routing_20261118/long/summary.json) · [计时代码](evidence/gqa_q1_routing_20261118/long.rs) · [时钟及恢复](evidence/gqa_q1_routing_20261118/long-clocks.json)

## 单层 decode 路径对照

Qwen3-4B，Hq/Hkv=32/8，D128，KV tile512，RKNPU 0.9.8。三核 NPU 1 GHz，CPU4–7 为 2.4 GHz，DDR 2.112 GHz，OpenMP 四线程、PASSIVE。输入来自 WikiText 前 4096 token 在第 17 层的真实 post-RoPE Q/K 与 V。16K/32K 单算子数据按 4096 个位置周期延长，仅用于测同一几何和输入分布下的耗时。每个长度取最后 512 步覆盖完整 KV tile，每步调用公共 `decode_step`，包含真实 append、同步、tail、跨 32-token 边界建图、QK、softmax、PV 及 FP32 输出。每进程先跑完整 512 步预热，再 truncate 并重放，报告 512 次调用的平均墙钟，再对正反两个进程求平均。逐步测量进程 CPU 核时。预装前缀和写测试文件在计时外。[探针](evidence/gqa_q1_routing_20261118/q1.cpp) · [板端时钟](evidence/gqa_q1_routing_20261118/probe-clocks.json)

整 tile 方案只对末尾单 token 且 LUT 安全的请求放宽计算 span，上取整至已分配的下一个 512 边界。有效长度仍由真实 cache 长度决定。每步尾块整理从约 35–50 μs 降至接近零，但 QK/PV 平均要多处理 240 个位置；4K、16K 的完整耗时几乎没动，32K 的正反两对分别快 5.26%、慢 0.10%。关闭 LUT 的原有 CPU softmax 仍将 QK/PV 交给 NPU；与同批冻结基线比，三种长度的 CPU 核时增加 47%–69%，输出相对 L2 差约 0.17%–0.19%。这一差异没有外推为模型 PPL。[逐进程数据](evidence/gqa_q1_routing_20261118/probe/summary.json) · [整 tile 实验补丁](evidence/gqa_q1_routing_20261118/tile.patch)

## 再换计算路径的判断依据

该几何每个有效 KV 位置至少对应 `2 × 8 × 128 × 2 = 4096` 字节的逻辑 FP16 K/V，每位置约 `4 × 32 × 128 = 16384` FLOP，约 4 FLOP/byte。每生成一个 token，16K 和 32K 每层分别要访问 64 MiB 和 128 MiB 逻辑 K/V，36 层分别为 2.25 GiB、4.5 GiB。物理 V 还有分母及通道对齐；这里没有用逻辑字节推断 DDR 已饱和。旧版三核 decode 降 DDR 频率更敏感，可作为优先测 KV 读取的依据。[既有单变量降频数据](../../lowlevel/tools/attention_prefill_probe/MULTICORE.md)

若目标是明显提升长上下文 decode，值得优先测 NPU 能直接消费的低精度 KV。只把 K 从 FP16 变成 INT8，K+V 的逻辑字节上限可减少 25%；两者均改成 INT8，理论上减半，实际还需存 scale。应把追加时量化、Q 或概率转换、按组尺度恢复和归一化全算进每 token 延迟，并以真实长文的 logits 和 PPL 检查数值。若每步先在 DDR 写回整份解压后的 FP16 KV，这套账会不同。已有 KV 量化研究显示 K、V 的合适量化粒度可以不同，RK3588 上的具体收益仍需板测。[KIVI 原论文](https://arxiv.org/abs/2402.02750)

按 KV 长度并行也是可选的 decode 映射，Flash-Decoding 展示过它如何利用 GPU 的空闲执行单元。本例已有 8 个 KV head 分配给 3 个 NPU 核；增加 KV 切分前，应确认能回收的长尾足以覆盖局部归约和额外提交。历史四大核 FP32 PyTorch CPU SDPA 在 KV4096 上最快记录约 3.41 ms，其软件、数据格式和测量边界与本轮不同；它不足以支持整段切到 CPU。[Flash-Decoding 作者说明](https://pytorch.org/blog/flash-decoding/) · [项目历史 CPU 对照](../../lowlevel/tools/attention_prefill_probe/DECODE.md)
