# Qwen3.5 C7 GDN prefill 分阶段计时与输入准备优化

四 token 输入准备将 C7 head-free pp512 的 GDN 输入准备从 171.4 ms 降至 113.4 ms，整模吞吐从 170.65 提升到 174.60 tok/s（+2.31%）。两者来自同进程交替对照。外层代码基线 `540e0c9`，native 基线 `dfd37e4`。

## 数据流及单算子验证

每四个相邻 token 的 K4 深度卷积共用四组权重和七行输入。普通数值走相同的向量 SiLU，超出原有范围时沿用每个向量的处理逻辑。Q/K L2 用四个 NEON lane 分别累加四行，保持每一行的通道、乘法和加法次序，写入原生布局时应用归一化系数。末尾 1–3 行沿单行路径处理。四个 CPU worker 继续按块和 head 分工。

单算子用 M128、chunk64、stride12352、非零初始卷积历史和递归状态，数据为确定性合成输入。每组两轮 ABBA，每进程预热两次、测十二次。下表中两组基线分别取各自配对的 48 次调用。

## 整模吞吐与 CPU 开销

独立进程、关闭 trace 的 ABBA，每组两进程，每进程预热一次、正式三轮。基线 166.74、优化 175.85 tok/s（+5.46%）。独立进程中的 Linear 墙钟亦从 1960.4 变为 1854.4 ms，这部分差异的来源尚未定位。同进程交替对照使用同一模型、工作区和动态库，两条路径编入同一个诊断库。三个 ABBA 轮次中每个样本的 trace 均确认 96 次调用采用同一条路径。三个四轮组中，两次基线与两次优化的平均 pp512 耗时差分别为 57.5、75.0、71.2 ms。固定 seed 42 的 pp512 后执行 1 步 decode，pp 计时排除 LM head 和 decode。

同进程每轮 prefill 的进程 CPU 时间约 6.559 → 6.320 核秒，四大核平均占用约 54.7% → 53.9%。全进程 CPU 率由小核采样器读取 CLK_TCK 并在 prefill 边界插值。GDN 调用区间的进程 CPU 时间由 getrusage 累加，为 1.659 → 1.423 核秒。

## 正确性与复现

算子级逐字节对照覆盖 M1/2/3/4/7/13/64/65/128/129、普通与补偿 TF32、非零 state 和 history、有步长且 padding 为 NaN 的输入。逐项比对输出、最终递归状态与卷积历史。短窗口数据包含触发 SiLU 回退的数值。静态库 device 测试覆盖 FP64 递归参考、原地更新、跨 chunk、两种 head mapping 与多种核心配置。固定 512-token 输入及 128 个强制 continuation 的 129 × 248320 个 FP32 logits 与此前同配置基线逐字节一致。

RK3588 zt-firefly，CPU4–7 固定 2.4 GHz，NPU 三核 1 GHz，DDR 2.112 GHz，ctx640、ubatch128、单 prefill 通道、普通 TF32。算子编译为 Clang 22、-O3、-ffp-contract=off、-mtune=cortex-a76。独立进程实验用同一 Rust 可执行文件加载不同 native 库。各版策略缓存均为 92 命中、8 未命中，在线调优和权重重载均为零。对照、探针与采样器置于实验目录。

使用 trace 构建并启用 `rknpu` 分类后，每次成功调用都可从 `gdn.timings` 事件的 `debug.*_us` 参数读取阶段时长。表中 sync 为调用同步操作所在区间的墙钟，硬件时长取自驱动。独立基线 trace 三轮的状态布局及同步合计 83.34 ms。若保留每层 native 状态并理想省去四个 ubatch 间的三次往返，按均摊估算可省约 62 ms。实际收益取决于状态缩放、缓存所有权及 prefill 到 decode 的交接。
