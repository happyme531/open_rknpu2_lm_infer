**下一步优化判断**

3草稿这份trace的总时间为130.38 ms/实际输出token，独立于正式测量的128.19 ms/token。分解如下：

| 主线程区间 | ms/输出token |
|---|---:|
| 专家complete-call | 27.796 |
| 等待record | 20.335 |
| 主线程导入/交换 | 4.103 |
| 其余验证：投影、shared FFN、GDN、CPU、head及编排 | 55.138 |
| 草稿生成 | 18.569 |
| commit | 2.348 |
| 外层采样/输出等 | 2.088 |

等待中约13.96ms发生在所消费记录的RAM-ready之前，约6.37ms在RAM-ready之后；前者与该记录pread重叠约13.76ms，读前排队仅约0.02ms。这是时间戳归因，后者包括后台导入和唤醒，未独立测量因果贡献。

未观察到3草稿decode被32条逻辑读缓冲上限持续阻塞。实际读取202.53MB/输出token，其中约41.21MB超出实际cold需求；目标是减少无效读取和可见等待，无须追求全程满盘。

1. 优先细拆算子完整调用和提交路径。专家调用约27.8ms/token，约21.8次/token；直接接出已有`rk_npu_moe_w8_timings`，分开gate、down、CPU middle、gather、build和sync。其余验证还有55.1ms，需要补dense投影/shared FFN阶段标记后再选具体GEMM。当前trace不能把这些时间归为纯NPU硬件计算。
2. 调度侧优先提高预取有效性，再评估读取直接进入NPU缓冲。继续扩队列或仅优化主线程4ms左右的导入，单独收益空间较小。合并hot/cold小调用须同时检查是否损失现有I/O重叠。
3. 维持3草稿作为当前主配置，再分别测草稿网络、共享head和Markov修正。新版7草稿接受率较低；直接增到15不能保证加速。

同预算缓存回放：每层候选32/40/48/56/64槽、总1600槽不变，针对本条trace选配后，cold记录仅从12926降到12820（0.82%）。这是固定路由的离线估算，未测新时序与额外workspace内存；这条候选分配路线优先级较低。
