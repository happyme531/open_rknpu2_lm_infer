# MiniCPM-V 4.7 35B-A3B：RK3588 MoE 流式加载复盘

2026-11-02。范围为专家存储、缓存、预取、加载与计算重叠，以及与投机解码的配合。依据 2026-10-19 至 10-29 的源码、冻结实验报告、原始 trace 和对话记录整理；本轮没有重新运行板端实验。

## 1. 完成了什么

在 **8GB RK3588 单板上，用本地 NVMe 保存大部分路由专家，完成 MiniCPM-V 4.7 35B-A3B 的真实文本生成**。CPU 负责路由、部分状态和中间处理，热、冷专家最终均由 NPU 计算。专家缓存容量可配置，支持预取、异步导入、槽位交换和 DSpark 投机解码。

最明显的收益来自三个层次：

1. **减少重复读取。** Prefill 改为按逻辑 chunk、逐层汇总专家并集，在 pp512 样本中把专家读取从 16,289 条降到 6,498 条；eMMC 上 prefill 从 108.879 秒降到 42.359 秒。
2. **摊薄每个输出 token 的完整执行成本。** DSpark 配合 M≤16 的专家缓存、LES 和导入调度，在一组 WikiText 对照中把普通 AR 的 5.374 tok/s 提高到 DS3 的 8.084 tok/s。
3. **有损地减少实际工作量。** 可选低权重专家跳过，在另一组 40 槽 WikiText 对照中把 7.817 tok/s 提高到 10.218 tok/s，同时必要冷权重流量减少 52.6%；小样本 PPL 有明显变化，默认关闭。

最终能力需要按输入和配置描述：

| 测量场景 | 缓存与配置 | Decode 实测 |
|---|---|---:|
| 10-27 WikiText pp512/tg128 | 40 槽/层，DS3，完整 top-8 | 7.817 tok/s，两次均值 |
| 同轮 WikiText | 40 槽/层，DS3，跳过阈值 0.10 | 10.218 tok/s，两次均值 |
| 10-29 两条 Alpaca 日常指令 | 默认 20 槽/层，DS3，完整 top-8 | 6.15 / 6.00 tok/s |
| 同轮 Alpaca | 默认 20 槽/层，DS3，跳过阈值 0.10 | 7.72 / 7.73 tok/s |
| 10-29 两条 Arena-Hard 开发请求 | 默认 20 槽/层，DS3，完整 top-8 | 4.92 / 5.74 tok/s |
| 同轮 Arena-Hard | 默认 20 槽/层，DS3，跳过阈值 0.10 | 7.89 / 8.03 tok/s |

后三组每个输入、每种配置各一次；不是数据集均值。WikiText 的 8/10 tok/s 是已验证的特定配置结果，不能当作所有输入的默认速度。完整结果见第 7 节。

## 2. 问题规模与平台约束

### 2.1 模型和数据量

本轮主体是无自定义 SQ 的 QQQ compressed-tensors 权重。主要结构为 hidden=2048、40 层，其中 30 层 GDN、10 层完整 Attention；每层 256 个路由专家、top-8，专家 intermediate=512。路由专家 gate/up/down **全部 W4A8**，共享 FFN 与输出头 W8A8。早期 W4 gate/up＋W8 down 的估算不作为最终配置。

一个专家的三份 W4 主权重约 1.5 MiB；包含 scale、校正数据和对齐后的磁盘记录为 **1,597,440 B**。全体 40×256 个专家的记录约 **16.36 GB**，8GB 板无法全驻留。

| 每层缓存槽位 | 占 256 专家的比例 | 40 层 W4 主权重载荷，约值 |
|---:|---:|---:|
| 20 | 7.8125% | 1,200 MiB |
| 40 | 15.625% | 2,400 MiB |
| 64 | 25% | 3,840 MiB |

这些数值不包含非专家权重、草稿、KV/GDN 状态、staging、工作区、CPU 堆和部分元数据，不能当作 RSS。当前 `--expert-cache-percent` 默认 8，向下取整得到每层 20 槽；它是专家数比例。

### 2.2 RK3588 的特殊约束

- **CPU/NPU 共用 DDR。** 把冷专家交给 CPU 计算，并不会自动解决整机内存容量。当前路线让大多数专家留在 SSD，按需加载后仍由 NPU 计算。
- **NPU 需要原生布局与显式同步。** 标准量化 checkpoint 不能直接作为任意形状的 NPU 权重缓冲。必须预打包，导入时复制必要数据，并做 TO_DEVICE 同步。
- **可用物理内存和 IOVA 地址空间是两项预算。** 大块 DMA 映射、同一 domain 内的权重与动态工作区，曾触发 `failed to allocate IOVA: -12`；剩余 RAM 充足也可能分配失败。
- **小 M 完整调用开销明显。** 一个专家调用还包含 gather、输入量化、命令构建、同步、CPU SwiGLU/A8 量化和输出整理。不能只把 GEMM 硬件时间相加来预测模型速度。

因此，核心目标是同时控制常驻容量、必要冷流量、逐层截止时间和完整调用次数。

早期常驻/eMMC/NFS 对照使用 Firefly 大内存 RK3588；后期低内存验证使用 8GB H88K＋本地 NVMe。早期能容纳 64 槽的内存条件不作为 H88K＋DSpark 的容量保证。

## 4. 实际执行流程

### 4.1 存储与内存层级

离线准备将标准 checkpoint 中的专家转换为 `experts.npu`。文件头记录 geometry、源权重信息、记录大小及 stride；专家记录按 layer/expert 定位，4096 字节对齐。运行时保留非专家模型部分和每层小热窗口，大多数专家继续留在 SSD。

加载经过三个阶段：读取到可复用的对齐 RAM 记录；导入 NPU staging 或最终专家槽并同步；完成后由计算路径消费。**RAM-ready、staging-ready、NPU 持久缓存命中是不同状态。**

### 4.2 Prefill

1. 在逻辑 chunk 内逐层推进。Mixer 仍按实际物理 ubatch 执行，汇总本层所有 token 的真实路由。
2. 对当前层的专家需求去重；大于 16 行的路径按文件顺序读取冷专家。
3. 使用共享的 16 槽 cold bank 分组加载和计算，每份权重服务本逻辑块内选中它的全部行。
4. 需要保留给 decode 的 prompt-tail 专家直接进入最终 hot 槽，并在当前组参与计算。
5. 每个 token/rank 的贡献回写原位置，再按原顺序 FP32 FMA 归约，完成共享专家和后续层。

当前 prefill 不使用 LES 来预测下一层。跨逻辑块仍可能重读冷权重；前缀检查点也会切开逻辑块。10-28 的 prepared 计划接入保留了这种逻辑块语义，防止上层再次按 M128 物理步骤逐块跑完整模型而丢失权重复用。

### 4.3 DSpark decode

1. 配套的五层 FP16 草稿网络根据目标特征生成一块 proposal hidden；共享目标输出头得到基础 logits，再按前一 token 做 Markov 校正和采样。
2. DS3 通常将 anchor 与三个草稿组成 M4 目标验证。
3. 每个目标层先执行归一化、mixer 和投影，计算真实 top-8；启用专家跳过时在此过滤低分 assignment。
4. **当前真实冷需求先入队**，随后生成下一层 LES 预测；已在热缓存中的专家不再排预测读取。
5. 两个 reader 优先处理 demand。预测只提前读到 RAM，确认需求后才由一个 importer 导入 staging；主线程同时计算热专家。
6. 主线程消费已经导入的专家时交换 staging/hot 权重视图。尚未开始后台导入时可接管 RAM 记录同步导入；正在导入时等待完成。
7. 冷专家按 ready 状态分组执行。最后完成原 rank 归约、共享 FFN、后续层和输出头。
8. 接受草稿前缀，提交或重放必要的 GDN/Attention 状态，继续下一轮。被拒绝后缀已经造成的计算和读盘都计入成本。

投机验证所需专家并集可能超过缓存容量。当前实现先完成原 hot 贡献，再分组复用槽位；不会要求把整个 M16 专家并集同时放入小窗口。

## 5. 主要实现与收益

下表的每行使用各轮自己的对照。不能把这些百分比相乘，也不能把不同二进制、teacher-forced 前向和真实生成混成一条累计加速曲线。

| 工作 | 改变的主要成本 | 同轮结果 | 定位 |
|---|---|---|---|
| Prefill 逻辑块专家并集复用 | 必要读量 | eMMC pp512：108.879→42.359 s，吞吐 2.57× | 最大 prefill 收益 |
| 读取缓冲池、双 reader、最终热槽直接填充 | 分配、排队、重复导入 | NVMe pp：36.851→39.596 tok/s；AR decode：4.970→5.367 | 组合约 +7.4% / +8.0% |
| 确认需求后后台导入、staging/hot 交换 | 暴露的复制和同步 | AR decode：5.4108→5.5442 tok/s | 约 +2.47%，有限收益 |
| DSpark＋M≤16 调度 | 完整前向与调用成本/有效 token | AR 5.3738→DS3 8.0838 tok/s；DS3 原调度 6.1164→8.0838 | 约 +50.4%；调度适配本身约 +32.2% |
| 约两组 ready 冷专家 | 加载/计算重叠 | DS3：7.707→7.934 tok/s | ABBA 约 +2.95% |
| 按阶段回收工作区 | 内存压力 | 同进程释放约 329.49 MiB PSS | 资源收益明确，未证实独立吞吐提升 |
| 专家跳过 0.10 | 必要流量＋实际计算 | DS3：7.817→10.218 tok/s | 约 +30.7%，有损近似 |

前三行来自 teacher-forced 前向 benchmark：pp512 不含最终输出头，tg128 包含输出头和 logits 捕获。后续 DSpark/分组/跳过的吞吐来自真实生成 CLI，包含草稿、验证、提交和采样等开销。读盘与模型加载的计时边界也应以各报告为准。

### 执行基础：Grouped MoE 和物理专家槽接口

流式调度复用已有 grouped MoE：按专家收集本批有效行，组织 gate/up 与 down 的 NPU 任务，利用三个 NPU 核处理适合的任务分组。中间的 SwiGLU、动态 A8 量化及部分输出整理仍在 CPU；这里的完整 MoE 调用包含 CPU 和同步阶段。

底层增加了原生专家导出/导入、物理槽位映射、导入计时和槽位交换接口。逻辑 expert ID、实际存储槽和本次任务的行映射分别管理，使少量物理槽能够服务全部逻辑专家。共享 FFN 在当前框架中仍单独执行。

这层接口是缓存与加载调度的基础。本轮没有将 grouped MoE 开关做成冻结版本的完整生成消融，因此不单独赋予一个端到端提速百分比；最早按单算子时间累加的估计也不纳入最终性能结果。

### 5.1 原生专家记录和每层缓存

**思路。** 把在线加载变成固定位置的大块记录读取；用近期实际路由适应对话，而非永久锁定一组全局热门专家。

**实现。** `Store` 从不可变 checkpoint 派生原生记录。`Window` 维护 expert→slot 和访问年龄；优先使用空槽，淘汰时保护当前请求，尽量保护 LES 预测集合，再以 LRU 选择。预测集合不能阻止实际需求推进。槽位在导入成功后才发布。

物理 bank 的大块分配最终限制为较小的 16 MiB 分块，降低大块连续 IOVA 映射压力。缓存容量参数同时输出请求百分比、实际槽数和有效比例。

**收益。** 10-21 万兆 NFS 同一二进制、同一固定输入的容量探针如下；每档一次，均开 LES，尚未使用 DSpark。

| 槽/层 | 峰值 RSS GiB | 缓存 assignment 命中 | 必要 MB/token | 实际 MB/token | Decode tok/s |
|---:|---:|---:|---:|---:|---:|
| 20 | 3.709 | 57.58% | 216.84 | 227.36 | 2.025 |
| 40 | 4.969 | 71.85% | 143.91 | 159.13 | 2.860 |
| 64 | 6.481 | 82.51% | 89.42 | 106.70 | 3.905 |

在带宽紧张、内存有余量的该环境下，扩大缓存很有效。后期 8GB＋DSpark 场景的内存组成不同，不能直接沿用 64 槽；额外容量可能挤压工作区和匿名内存。见[缓存容量实验](MINICPMV47_CACHE_BUDGET.md)。

### 5.2 LES：免额外训练的下一层预测

**算法。** 用当前层 FFN 输入提前经过下一层 router，预测下一层 top-k。router 本身来自已训练主模型，LES 不需要单独的预测器权重或额外训练。到下一层仍执行正式 router；漏预测的专家照常加载和计算。[官方 LES 说明](https://github.com/OpenBMB/llama.cpp-omni/blob/a64932ec615e1463158129feaf2f0752d0c07a2e/docs/les/lookahead-expert-scheduling.md)

**实现。** 当前采用 CPU 浮点点积、按批调度线程池。M≤16 时逐行预测后取专家并集，过滤驻留专家，再排预测读取。队列以真实需求优先；generation 标识防止 reset 前的旧任务完成后污染新请求。预测错误主要增加磁盘过读；只有确认需求才能触发 NPU staging。

**收益与边界。** 10-21 无 SQ eMMC 的 top-8 召回约 81.18%，但冷需求在路由确认前完整就绪为 0%；提前开始的部分读取仍让 decode 从 1.022 提高到 1.096 tok/s。同轮万兆 NFS 对照从 1.967 提高到 2.099 tok/s，约 +6.7%。

缓存过滤后，剩余冷需求更难预测，冷需求覆盖率会低于全体 top-8 召回。该 NFS 样本中缓存命中 57.58%，冷需求预测覆盖 70.41%，冷需求提前就绪 7.58%。这三个比例不能互换。见[无 SQ 测试](MINICPMV47_NOSQ_BENCHMARK.md)、[NFS 对照](MINICPMV47_NFS10G_BENCHMARK.md)。

### 5.3 Prefill：逻辑块和专家分组 staged walk

**算法。** 参考 Strata 的短 prompt staged walk：先获得真实专家需求，再按专家处理一段逻辑 prompt，复用同一份权重。物理 GEMM 的 M 上限不应决定外层权重读取循环。

**实现。** 逻辑块最多 1024 token，NPU 物理 ubatch128。在 pp512 中汇总每层全部路由后，按专家并集读取、分组计算。需要保留的 prompt-tail 专家直接进入热槽；其余进入共享 cold bank。没有照搬 Strata 的 CUDA stream、GPU 页缓存或 CPU 专家分担路径。

**收益。** 原方案四个 M128 块各自跑完全部层，部分冷专家到下一个块必须重读。修改后，pp512 读取 6,498 条不同记录、10.380 GB，重复读从 9,791 条降到 0；完整 prefill 时间从 108.879 降到 42.359 秒。真实路由并不均匀：该输入平均每层需要 162.45 个不同专家，逐层为 122–252，不能按“所有专家均匀激活”代替实测。

10-28 又把逻辑块合并接入 prepared prefill，保证前缀计划和缓存检查点接入后仍保留这项复用；该接入做了数值回归，没有独立宣称吞吐收益。见[调度与读取统计](MINICPMV47_NOSQ_BENCHMARK.md)、[通用运行时接入](MODEL_RUNTIME_OPTIMIZATIONS_20261028.md)。

### 5.4 有界读取、对齐缓冲池和双 reader

**思路。** 在专家粒度上增加适量并发，复用大块对齐内存；让预测队列和读缓冲有明确上限。

**实现。** 两个 reader 共用 demand/speculative 队列；每代 ready＋in-flight 限制为 32 条。相邻真实需求最多八条合并成 `preadv`，直接写入各自已有的对齐记录缓冲，不读取未请求的间隙。空闲缓冲池最多保留 32 条记录；消费、取消和 reset 按所有权归还。O_DIRECT 限制专家数据在客户端页缓存中的额外驻留。

**收益。** 在 40 槽 NVMe 消融中，原始加载器 4.970 tok/s，单 worker 缓冲池 5.191，双 worker 缓冲池 5.421。最终再加入 prompt-tail 直接入热槽、逐组执行，prefill 36.851→39.596、decode 4.970→5.367 tok/s。

后者的 8% 是组合收益，不是双线程的单独收益；逐组版本相对另一个层尾执行版本更照顾 prefill。双 reader 也让更多错误预测在取消前读完，所以必要冷流量不变时，实际读量可能增加。见[I/O 消融](MINICPMV47_STREAM_IO_OPTIMIZATION_20261025.md)。

### 5.5 异步导入和槽位视图交换

**思路。** 预取到 RAM 后还有 NPU 导入复制与同步。把确认会用的记录提前导入独立 staging，再低成本切换到 hot 槽。

**平台实现。** 每个兼容的 NPU Backend/context 共享一个 32 槽 staging bank，按 domain 复用，避免每层各分配一份。一个独立 importer 处理确认需求；读线程继续读盘。staging 槽以独占 lease 管理，交换同时转移权重视图、scale、INT4 correction 和底层存储所有权；Reader 先停止并 join，再释放 bank/context。

槽位交换消除了 staging→hot 的第二次整份复制；SSD→RAM、RAM→NPU 的导入复制和同步仍存在。当前没有把 GPU 直接文件读取接口等价地搬到 RK NPU。

**收益。** 同轮普通 AR 从 5.4108→5.5442 tok/s，约 +2.47%。主线程导入/交换从 21.120 降到 3.545 ms/token，但 record 等待从 16.208 增到 25.112 ms；后台导入尚未完成的等待也落入 record 等待中。最终净省约 4.45 ms/token。

确认需求后导入还消除了推测性导入中约 23.4 份专家/token 的无用 NPU 复制。磁盘错误预取仍存在。原生探针中完整 import 从独立运行约 193 μs/专家变为与 NPU 计算并发时约 256 μs，说明并发资源竞争会抵消一部分重叠收益。见[异步导入实验](MINICPMV47_ASYNC_IMPORT_20261025.md)。

### 5.6 DSpark，以及 M≤16 流式调度

**算法。** DSpark 是需要配套草稿权重的投机方法。本项目直接使用对应 MiniCPM 草稿，没有重新训练；Markov/confidence 实现参考 [DeepSpec](https://github.com/deepseek-ai/DeepSpec)。块内 hidden 可并行产生，前一 token 相关的 Markov 校正和采样依次进行，再由目标模型验证。贪心模式按目标选择接受前缀；框架也有概率接受/残差分布路径。本报告的速度主要来自贪心测试。

**关键平台适配。** 流式路径原先只给 M1 启用 LES 和持久缓存调度，DS3 的 M4 验证因此失去这些机制。现在 1–16 行均可逐行预测、合并专家并集、按确认需求异步导入。并集超过 hot 容量时分组推进；有界 RAM 满时先消费任意已就绪记录，避免坚持等待某一个尚未读取的专家而阻塞队列。

**收益。** 同轮 production CLI 的 DS3 从 6.1164→8.0838 tok/s，约 +32.2%；相对同轮 AR 5.3738 约 +50.4%。包含 pp512 的请求总时间从 36.72→29.92 秒。收益同时包括小批量验证的计算摊销和恢复加载重叠。见[DSpark 与 M≤16](MINICPMV47_DSPARK_H88K_20261026.md)。

**大窗口的限制。** 同轮 DS7 为 8.069 tok/s，未超过 DS3。后续在数学样本上 DS7＋置信度截断曾有约 18% 收益，中文和英文样本则回退；10-29 两套真实指令中 DS7 同样慢于 DS3。目标是每单位时间产生多少有效 token，不能只追求接受率或每轮产出。

保留的一项草稿优化是先计算 learned confidence，省略已经决定丢弃行的 Markov 全词表投影；默认 cutoff=0 时继续完整校正。见[草稿窗口与投影实验](MINICPMV47_DRAFT_EXECUTION_20261027.md)。

### 5.7 Ready 冷专家分组

**算法与适配。** llama.cpp-omni 的两段执行提供了“前段计算覆盖后段加载”的思路。这里按 record 就绪状态分组：热专家先算；冷组至少等待约半批、且通常不少于三个专家，再领取额外 ready 记录并执行，其余读取/导入继续进行。

分组不能无限细化。完整 MoE 调用包含量化、gather、提交和同步，每来一个专家就提交会增加固定成本。各组贡献写回原 token/rank，最后保持原归约顺序。

**收益。** ABBA 中约两组策略 7.707→7.934 tok/s，约 +2.95%。诊断 trace 中 routed 71.612→68.821 ms/token；更细的小组调用次数为 5,461，约两组为 3,915，显示等待减少与调用膨胀之间的取舍。见[冷专家分组实验](MINICPMV47_READY_GROUPS_20261026.md)。

### 5.8 阶段内存生命周期和 IOVA 预留

**思路。** Decode 不继续保留只服务大 M prefill 的全部工作区；评分时再按需创建。缓存预算必须为草稿和执行资源留余量。

**实现。** 输出头只预热生成实际会使用的行数；进入 decode 时释放 prefill 专用 Linear workspace。共享一份分页贡献、gather、scatter 工作区，减少跨层重复分配。为 streaming domain 的非权重工作区预留从 128 MiB 增至 512 MiB，降低权重装满地址域后再创建 staging/workspace 的失败风险。

**收益。** 独立同进程观测 PSS 5167.82→4838.33 MiB，释放约 329.49 MiB；单次切换约 165 ms。没有证实该改动独立带来 decode 提速。分页工作区复用的另一轮 prefill 13.1205→12.7721 秒，约少 348 ms，decode 未确认改善。

这些是实际资源和生命周期收益。统计中的 workspace payload 包含 host/device 分配，减少的 payload 不等于等量物理内存。见[阶段与内存实验](MINICPMV47_STRATEGY_EXPERIMENTS_20261026.md)、[分页工作区](MINICPMV47_PAGING_WORKSPACE_20261026.md)。

### 5.9 可选低权重专家跳过

**算法。** 参考 Strata 的 `STRATA_DS4_DISK_SKIP_W`：用路由分数决定是否省略小贡献。原参考模式针对 decode/verify 的冷专家；当前实现扩展到 prefill/decode 的冷热专家，对归一化 top-8 中严格低于阈值的 assignment 置零，最高分始终保留，剩余权重不重新归一化，共享专家保留。

**实现。** 在实际需求、LES 预测、缓存 touch、prompt-tail、gather、原生 GEMM 构建和输出归约中一致过滤。不能仅把最终输出乘零，否则专家仍会读盘、导入和计算。零阈值有直接计数路径，不再复制或反复扫描路由权重。

**同轮 40 槽 WikiText 结果：**

| 阈值 | 平均执行专家/层/行 | 必要冷读 MB/输出 token | Decode tok/s | PPL，256 个评分目标 |
|---:|---:|---:|---:|---:|
| 0 | 8.000 | 161.32 | 7.817 | 5.324853 |
| 0.05 | 7.880 | 158.22 | 8.082 | 5.508891 |
| 0.10 | 4.851 | 76.39 | 10.218 | 5.625887 |

0.10 跳过 39.36% 的 decode assignment，必要冷流量降 52.6%，速度提高 30.7%；PPL 上升约 5.65%，平均丢失 top-8 内部归一化权重质量 25.44%。PPL 变化不能翻译为任务准确率只下降同样百分比。该档已经改变模型计算和生成文本，默认关闭；0.05 的流量收益很小，也不能据小幅测速差值认定更好的质量/速度平衡。见[专家跳过与质量筛查](MINICPMV47_EXPERT_PRUNING_20261027.md)。

### 6.1 分层缓存为什么没有继续

最终尝试并非简单“哪层命中率低就多给槽”。固定总数 1600，先回放每层不同容量的 miss 曲线，再用动态规划最小化总冷读；相同读量优先接近均匀分配。直接按 assignment miss 率比例分配，在校准 trace 上反而增加约 1.7%–2.0% 冷记录。

| 输入与阈值 | 均匀 40 槽 tok/s | 分层 tok/s | 必要 MB/token，均匀→分层 |
|---|---:|---:|---:|
| Wiki，关闭跳过 | 7.981 | 7.736 | 161.32→158.72 |
| Wiki，0.10，ABBA 均值 | 10.230 | 10.527 | 76.39→72.21 |
| 独立中文，0.10，单组 | 7.759 | 7.687 | 64.31→65.38 |

均匀和分层的总槽数、设备权重与 staging 相同，并处理了不同容量 bank 之间的 workspace 复用，避免额外工作区干扰比较。校准内收益仍较小，跨输入没有保持。

原因包括：每层 miss 曲线随输入改变；降低必要冷读没有同比降低错误预取；容量改变也影响 ready 分组与计算重叠。另一条按可见等待成本加权的探针仅得到 10.239 tok/s，未改善均匀对照。

截至本复盘，相关更改保存在主仓库 stash `f32b093` 和原生库 stash `e665faa`，当前代码没有 `--expert-cache-plan`，各层继续使用统一槽数。这组结果限制的是已测试的静态方案，不证明所有动态分配算法均无效。

其他负结果见[策略实验](MINICPMV47_STRATEGY_EXPERIMENTS_20261026.md)、[草稿实验](MINICPMV47_DRAFT_EXECUTION_20261027.md)、[TF32 router 实验](MINICPMV47_ROUTER_TF32_20261026.md)。

## 8. 瓶颈与总体分析

### 8.1 缓存减少字节，预取改变截止时间

普通 AR 一 token 每层选八个不同专家时，可以近似写为：

`必要字节/token = 40 × 8 × 1,597,440 × (1 − assignment 缓存命中率)`

这能解释早期 20 槽、57.58% 命中时约 216.84 MB/token 的必要冷流量。LES 正确预取仍会消耗这些字节，收益来自提前完成一部分传输。

DSpark 需要改用每次验证、每层的专家并集：

`必要字节/输出 token = record_stride × Σ(本次验证实际未驻留的不同专家数) / 实际输出 token 数`

被拒绝行的专家和执行也在求和中。实际 SSD 读量还包含错误/取消预取，以及统计窗口边界的在途读取。不能把必要流量当实际 I/O，也不能把冷权重流量简单除以投机窗口长度。

### 8.2 命中率必须区分分母

| 指标 | 分母与含义 |
|---|---|
| Assignment 缓存命中 | token×top-k 分配中，真实路由确认时已在持久 NPU 窗口的比例 |
| Unique 缓存命中 | 每次层调用专家并集中已驻留的比例；更贴近记录读量 |
| 全体 LES recall | 预测集合覆盖真实专家的比例；批量并集与逐行同位置召回应分开 |
| 冷需求预测覆盖 | 实际冷专家中，之前已经排入预测的比例，包含仍排队者 |
| 冷需求 RAM-ready | 实际冷需求确认时，完整记录已经读到 RAM 的比例 |
| Staging 完成/使用 | 已完成 NPU 导入并可交换的数量；可包含确认后才按需读取者 |

缓存变大后，整体读量下降，同时剩余冷集更难预测，冷需求 LES 覆盖率可能下降；这两个现象可以同时成立。

启用专家跳过后，缓存及 LES 的相关分母只包含保留的实际路由分配，不能把命中率变化全部归因于缓存替换策略。

### 8.3 SSD 带宽重要，但推理不应以持续跑满盘为目标

早期 eMMC 专家读取约 0.25–0.29 GB/s，万兆 NFS 实际供给约 0.5–0.6 GB/s，流式 decode 的确主要受传输限制。H88K 本地 NVMe 上，固定实际专家序列纯 I/O 回放约为单 reader 2.304、双 reader 3.007、四 reader 3.119 GB/s；双 reader 之后继续加线程的收益已小。

Decode 主要是约 1.5 MiB 专家粒度的大块随机读，prefill 才有更多相邻记录合并。存储探针应优先回放真实专家序列或相近的低队列大块访问，不能从 4K 高并发 IOPS 直接推导本应用性能。

这些是独立 I/O 探针。模型还有逐层路由依赖、RAM→NPU 导入、同步和计算，实际整段平均流量会低得多。预取更积极还会增加错误读取并争用 DDR。某次读盘空闲可能是目标模型正在生成下一层路由，不能一律解释为调度失误。

### 8.4 大收益之后，关键路径已分散

以下重列 10-27 **40 槽、DS3、跳过 0.10、WikiText** 的诊断 trace，按 128 个实际输出 token 归一化。它用于解释该配置的预算，不代表当前默认 20 槽或自然指令的预算。

| 主线程或其完整调用阶段 | ms/输出 token |
|---|---:|
| 路由专家完整调用 | 21.8 |
| Mixer 投影、GDN、Attention | 21.5 |
| 草稿网络、共享输出头、Markov | 16.6 |
| 冷记录等待、主线程导入/交换 | 11.6 |
| Router、LES、需求管理 | 7.7 |
| 共享专家、目标输出头 | 11.4 |
| 其他及提交等 | 10.9 |
| 合计 | 101.5 |

嵌套 span 没有重复计入，后台读取和导入时间不另加。正常无 trace 的该组吞吐约 10.22 tok/s，诊断 trace 更慢。

冻结其他耗时、将上表 11.6 ms 全部消除，仅对应约 13% 的理想吞吐收益；实际只能兑现一部分。这解释了后续队列、缓存、分配小改动越来越难再得到 DSpark 那样的提升。

该剪枝 trace 的必要冷流量为 76.39 MB/输出 token，实际读约 100.96 MB。仍有减少错误预取的空间，但流量变化需要结合暴露等待、导入和完整计算重新评估。

### 8.5 下一阶段值得研究的空间

**投机策略和草稿成本。** 另一轮关闭专家跳过、40 槽的“已知正确未来 token”实验中，verify1/4/8/16 的真实目标吞吐为 5.40/10.62/13.37/15.07 token/s，包含专家加载、目标头与状态提交。这证明小批量目标执行存在摊薄空间；实验不含草稿和拒绝成本，15.07 不能当作可直接实现的端到端速度。应根据最近有效产出、验证成本和冷流量选择窗口，并降低草稿词表投影成本。见[目标侧验证曲线](MINICPMV47_STRATEGY_EXPERIMENTS_20261026.md)。

**完整 MoE 执行接口。** 当前 paged 路径仍把 token/top-k 展开成 assignment 行，热、冷组各自进入完整 native 调用。原始输入量化复用、稀疏 job 描述、更少的 gate/down 提交边界和冷热/共享工作统一调度，属于较大的执行器改造方向。仅挪走 CPU SwiGLU 或继续切小冷组，预算有限。

**有损近似的质量/成本平衡。** 现有跳过已经证实“大幅减少真实工作”可以提速；下一步若按层或按概率质量调整，应以更完整任务质量和 PPL 评估为前提。当前证据不足以设置新的默认阈值。

## 9. 正确性与证据边界

性能工作采用固定频率、共享板锁和正式/trace 分离。较成熟的改动使用 ABBA 或正反顺序；单次样本、独立探针、回放和知道未来的 oracle 均单独标注。没有把后台 service 时间直接加到主线程 wall time。

主要正确性手段是完整 FP32 logits 对照和物理槽位时序审计。关闭有损跳过时，多轮存储、缓存、并发和分组改动均通过固定输入对照。10-28 的生命周期修复额外验证：

- 第二个 reader 或 importer 创建失败时，已启动线程退出并释放 Store 引用；
- decode 后追加 `[128, 4, 16, 32, 4, 32, 1]` 批次，两次 M32 均没有遗留 staging 导入；
- 单行、M4/M16 的 3,722,160 个 FP32 logits 与固定参考相同；追加 prompt 的 1,737,008 个值在预取开关之间相同。

后续原生修复还明确了交换槽位后的底层 buffer 所有权和跨线程使用边界。正确的依赖顺序是：完整读取、导入与 sync 完成、发布槽位、执行，最后释放或归还资源。

结论适用范围：

- 本文主要是文本推理；这些速度不代表图像编码、视觉 prefill 或多模态任务质量。
- 多数消融仅覆盖少量固定 prompt；任务、上下文、缓存容量、算子版本和草稿接受率都会改变结果。
- 部分早期 8GB DSpark 样本存在 VmSwap，进程峰值不等于 decode 阶段的换页 I/O；不能把全部波动归因于某一优化。
- 原生算子更新会改变舍入、路由和接受率，跨版本结果不能只解释为算子快慢。
- 专家跳过的 256-target PPL 仅为小样本筛查，尚无充分依据量化实际任务能力损失。
- SSD 经转接链路，历史存在可纠正 PCIe 错误；本文采用实际连接下的测量，不外推更换硬件后的速度。
