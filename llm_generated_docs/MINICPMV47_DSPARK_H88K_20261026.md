# MiniCPM-V 4.7：DSpark 与 M≤16 专家预取

测试日期：2026-10-26。直接使用项目现有 production `run` CLI、共享投机采样和状态提交路径。目标模型使用本地 SSD 的 stream 专家存储。

正式测量：普通 AR **5.3738 tok/s**，DSpark 3草稿 **8.0838 tok/s**，7草稿 **8.0690 tok/s**；相对本轮 AR 约 **+50.4%**。3草稿相对修改前调度约 **+32.2%**。包含 pp512 的请求总时间从 **36.72秒**降到 **29.92秒**。

**实现**

- `DECODE_BATCH_MAX_ROWS = 16`：1–16 行启用每行 LES，合并专家并集后预取；实际 demand 确认后异步导入，完成后交换 hot/staging 槽。
- 缓存可容纳整个请求时保护全部请求专家；专家并集超过槽数时，先完成原 hot 专家的贡献，再分组导入、计算冷专家，复用同一组槽。
- 消费已就绪记录后再等待其他记录，使超过 32 个专家的请求能够在有界读缓冲内推进。
- pp512 继续走大批 prefill 的文件顺序和 prompt-tail seed 策略；C++ 算子和矩阵计算没有修改。

**测试口径**

- H88K，8GB RAM，`user@fe80::1828%enp3s0`；GM7 本地 NVMe，PCIe Gen3 ×4。
- CPU4–7 2.4GHz，NPU mask7 / 1GHz，DDR2112MHz；逐例独占锁并恢复时钟。未调整 swap、内核或 PCIe。
- noSQ MiniCPM-V 4.7 35B-A3B，routed 专家 gate/up/down W4A8，shared FFN 与 lm_head W8A8；DSpark 5 层 FP16 草稿。
- 同一条 raw WikiText prompt，严格重编码核对为512 token；ubatch128，ctx1024；生成129 token，包含首个 prefill 采样 token，因此计时 decode 为128 token。
- greedy，temp0，top-k0，top-p1，seed42，no-tune；每层40个缓存槽，LES开，O_DIRECT开，两条读线程，一条导入线程。
- 速度为 `128000/decode_ms`，包含草稿、验证、接受判断、commit/replay、采样与文本输出；排除权重加载和 prefill。组合速度用总token/总时间换算。
- 正式测量采用默认分配器；trace 单独设置 `MALLOC_MMAP_THRESHOLD_=131072`，不计入速度均值。

**验证与限制**

- ARM release 构建、12项专家存储/队列/窗口测试、all-target Clippy `-D warnings` 通过。回归测试覆盖预取填满32个读缓冲后，真实路由首先需要未读取专家的情况。
- 本轮完成的9个 production CLI 样本的生成文本均与同一 AR 基线一致；计数均为512 prompt、129 completion、128 timed decode。未捕获完整 token ID 或 FP32 logits，不作 logits 精确一致的声明。
- 各样本的时钟恢复成功。内存表中的换出是进程 VmSwap，不等于磁盘写入；系统使用 zram，未改变 swap 策略。
- 结果来自单一 WikiText 续写，接受率和最优草稿长度随任务变化。每组1–2次只用于本机方向判断。
