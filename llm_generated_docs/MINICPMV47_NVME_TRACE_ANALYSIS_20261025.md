# MiniCPM-V 4.7 NVMe Trace：带宽利用和下一步优化

2026-10-25。分析 H88K 8GB 上已有 pp512/tg128 数据，物理 ubatch128，CPU4–7 2.4GHz、NPU mask7 1GHz、DDR2112MHz。模型为无 SQ 版本，路由专家 gate/up/down 全 W4A8。这里未运行新的推理、修改调度或修改板端配置。

## 结论

当前推理没有持续跑满 SSD 带宽。源码可见单 IO worker、每次读取重新分配大块对齐缓冲区、路由依赖、导入和计算交替执行这些环节；尚未分离出分配、CPU/DDR 竞争各自对吞吐差距的贡献。读取加速仍有收益，但现在端到端已有较大比例的固定计算和导入开销。

优先做可复用对齐缓冲区，再配合两个 IO worker，并保留真实需求优先和有界预取。Prefill 应把主要精力转向专家完整调用和导入路径；仅消除现有等盘时间，在其他阶段不变时只能提高约 6–8%。

## 带宽证据

下表使用不记录 trace 的正式样本，每档预取开启、两次重复。MB/GB 均为十进制。读取服务吞吐按两次总字节 / 总读取服务时间聚合；它包括缓冲区准备和读取调用，不是设备内部吞吐。

| 每层槽数 | tg tok/s | 实际 MB/token | 全 decode 平均专家流量 GB/s | 读取服务吞吐 GB/s | 读取服务时间 / decode 时间 | 主线程等数据 ms/token |
|---:|---:|---:|---:|---:|---:|---:|
| 20 | 4.559 | 261.14 | 1.191 | 1.568 | 75.9% | 35.66 |
| 40 | 5.018 | 181.00 | 0.908 | 1.394 | 65.2% | 29.85 |
| 56 | 5.445 | 136.35 | 0.742 | 1.335 | 55.6% | 24.15 |

同一块盘、同一批 4096 条实际 decode 专家记录，使用 O_DIRECT、每线程复用一个对齐缓冲区，纯 IO 回放结果为：

| IO worker | 聚合 GB/s | 相对单线程 |
|---:|---:|---:|
| 1 | 2.304 | 1.000× |
| 2 | 3.007 | 1.305× |
| 4 | 3.119 | 1.354× |

同目录 fio 的顺序 1MiB 样本为 QD1 2.497GB/s、QD8 3.054GB/s。实际专家回放已经证明两个 worker 接近当前连接下约 3GB/s 的能力，四个相对两个仅多约 3.7%。纯 IO 与推理并行时的 CPU、DDR 竞争不同，不能把这 30.5% 直接套到 token 速度上。

整盘 250ms 采样也支持没有持续满带宽：20/40/56 槽两次 decode 整盘平均分别约 1.11–1.26 / 0.889–0.903 / 0.729–0.742GB/s；区间内最高单个采样分别约 1.70 / 1.35 / 1.24GB/s。这些是整盘计数和外部阶段快照，边界与精确的进程计时有少量偏差，也不能排除采样间隔内更短的高带宽突发。

较大缓存使流量下降，本来就不要求盘持续满带宽。优化目标应是缩短关键路径上的等待及导入，而不是提高磁盘利用率本身。

## Decode 关键路径

以下按正式计时与运行时累计阶段统计拆分，单位 ms/token。主线程的这些区间可相加；后台读取服务时间与它们重叠，未再加入总和。

| 阶段 | 20 槽 | 40 槽 | 56 槽 |
|---|---:|---:|---:|
| 等待专家记录 | 35.66 | 29.85 | 24.15 |
| 专家导入，含复制及 sync | 33.59 | 22.40 | 15.72 |
| 路由专家完整 execute 调用 | 45.48 | 43.86 | 41.82 |
| 其余 Linear 和 MoE 编排 | 59.69 | 59.01 | 58.08 |
| LM head | 18.00 | 18.03 | 18.14 |
| CPU GDN 阶段 | 10.65 | 10.27 | 10.13 |
| GQA attention 阶段 | 2.63 | 2.50 | 2.72 |
| CPU 阶段，包括路由、预测和归一化等 | 12.20 | 11.91 | 11.44 |
| 其他未分类时间 | 1.46 | 1.46 | 1.45 |
| 总计 | 219.34 | 199.29 | 183.65 |

`linear_ms` 包含整个 paged bank 调用及非专家投影。表中的“其余 Linear 和 MoE 编排”是 `linear_ms − wait_ms − import_ms − compute_ms`，还不能把其中 59ms 全部归为硬件矩阵乘法。“专家完整调用”包含输入整理、激活量化、提交、同步和输出处理，不是 NPU 硬件执行时间。

![正式 decode 阶段拆分](evidence/minicpmv47_nvme_h88k_20261025/formal_after_clean/decode_stage_breakdown.png)

在其他耗时不变、仅把当前 `wait_ms` 清零的理想假设下，20/40/56 槽分别从 4.56/5.02/5.45 提至约 5.44/5.90/6.27 tok/s，吞吐收益约 19.4%/17.6%/15.1%。这只约束“隐藏当前等待”的收益，不是缓存、计算、内存竞争等优化的共同上限。

## Trace 显示的调度问题

两份独立 trace 均使用下一层 LES 预取。20 槽路由区间内后台读取服务覆盖约 94%，56 槽约 76%；服务区间包含缓冲区准备，不能解释为 SSD 总线占用率。正式无 trace 的服务时间占比分别只有约 76% 和 56%。

| Trace 指标 | 20 槽 | 56 槽 |
|---|---:|---:|
| LES 预测到实际路由，平均 ms | 7.60 | 5.08 |
| 预取入队到开始读取，平均 ms | 5.75 | 3.66 |
| 已开始预取距实际路由，平均 ms | 2.28 | 2.47 |
| 单条预取服务，平均 ms | 1.95 | 2.03 |

后面三行按同一 `(layer, expert)` 的入队、读取与随后的实际路由匹配，分别覆盖 9982/6054 条；29/12 条无法满足“实际路由标记之前已开始读取”的匹配条件，未纳入。第一行按全部 4992 次层间预测统计，样本集合不同，均值不能直接相减。

这说明提前量有相当部分耗在当前需求和其他读取之后排队。双路读取值得尝试；也应避免预测在队列中积压后才启动。

预取的额外流量同样明显：

| 槽数 | 必要 MB/token | 额外 MB/token | 无用读取 / 实际读取 |
|---:|---:|---:|---:|
| 20 | 216.84 | 44.30 | 16.97% |
| 40 | 143.91 | 37.10 | 20.50% |
| 56 | 103.98 | 32.37 | 23.74% |

较大缓存过滤了很多容易预测的需求，剩余冷需求的预测覆盖更低；总 LES recall 仍约 81.18%。当前预取总体有效，开预取的 decode 吞吐比关闭提高约 21.3%/16.6%/13.1%。但更快、更并发的 IO 会让错误预测更早完成，不能只追求发起更多预取。

预取目前只把记录读到主机缓冲区，真正导入 NPU 仍在主线程上完成。源码导入路径包含 gate/up、down 权重及元数据复制，并分别执行 TO_DEVICE sync，因此“预取已就绪”仍有后续导入成本。

## Prefill：读量正确，主要瓶颈已转向计算和导入

两份 trace 都读取 6498 个不同的层/专家，共 10.380GB；每个只读一次，重复读取为零。logical prompt 为 512，mixer 仍按物理 ubatch128 执行。

| 正式阶段，秒 | 20 槽 | 40 槽 | 56 槽 |
|---|---:|---:|---:|
| pp512 总时间 | 13.458 | 13.940 | 14.338 |
| 等专家记录 | 0.722 | 1.007 | 1.102 |
| 专家导入 | 1.755 | 1.943 | 2.071 |
| 专家完整 execute 调用 | 5.342 | 5.365 | 5.223 |
| 其余 Linear 和 MoE 编排 | 2.094 | 2.102 | 2.127 |
| CPU GDN 阶段 | 1.405 | 1.428 | 1.398 |
| CPU 阶段 | 1.757 | 1.709 | 1.736 |
| GQA attention 阶段 | 0.260 | 0.261 | 0.559 |
| 其他 | 0.124 | 0.126 | 0.123 |

40 槽下等盘占 7.2%，专家完整调用占 38.5%。单独清零当前等盘时间的吞吐收益约 7.8%。

Trace 的相邻 routed 区间之间合计约 5.05/5.08 秒，内部没有后台读取。由冻结源码时序可知，其中包括当前层共享 FFN、残差处理、下一层 mixer 及路由；并非主线程空转。下一层真实专家依赖这些结果，当前也没有 prefill LES。不能把这 5 秒直接宣称为可通过预取消除的时间。

另一个可具体改进的点是缓存预热重复导入：20/40/56 槽都只读 6498 条，却分别导入 7298/8098/8738 次。需要留到 decode 的专家先进入 cold bank 计算，再从同一主机记录复制进 hot bank，多了 800/1600/2240 次导入，没有重复读盘。可评估直接导入最终 hot 槽并参与 prefill 计算；这会改变分组及读取顺序，须比较调用批量和 IO 合并效率，不能只按减少复制次数预测端到端收益。

## 下一步顺序

1. **对齐缓冲区池 + 双路 IO。** 先比较现状单线程、池化单线程、池化双线程，把分配和并发收益分开。保持真实需求优先，ready 与 in-flight 共同限额。现有 `in_flight.clear()` 和单 worker 生命周期需要配套改成按任务回收，不能直接多启动一个线程。以 40 槽无换页配置做主对照。
2. **降低导入成本，减少 prefill 重复导入。** Decode 的 22.4ms/token 和 prefill 的 1.94s 都是可见主线程开销。先拆 memcpy 与 TO_DEVICE sync；评估预热专家直接入热槽，及安全槽位上的导入重叠。不能覆盖仍在执行或待归约的专家槽。
3. **计算路径按真实形状拆分。** Prefill 优先看约 5.36s 的专家完整调用；decode 同时拆约 59ms/token 的其余 Linear 与 MoE 编排，补上共享 FFN、mixer 投影的阶段标记，再决定具体算子。当前粗粒度 trace 无法指出这 59ms 中哪个算子最大。
4. **结合预取无效流量验证双路调度。** 记录真实需求排队、预测排队、提前就绪率、取消时状态和实际总字节。检查双路 IO 的等待下降是否被无效读取或 DDR 竞争抵消。仅在这些数据支持时扩大预取深度。

## 证据范围

- 正式结果是每档两次的冻结 2026-10-21 二进制，所有完整 tg128 FP32 logits 与常驻基线逐字节一致。这里依据冻结源码解释阶段统计；当前源码已有清理，未用新计数口径解释旧数据。
- Trace 独立运行，额外设置 `MALLOC_MMAP_THRESHOLD_=131072`；记录和分配方式明显拖慢执行。只用其判断顺序、重叠、槽位和排队现象，绝对时间、速度和理想等待上限使用无 trace 正式样本。两份 trace 共 409600 次物理槽位检查，违规为零。
- 56 槽正式样本出现少量进程换页，40 槽没有；不把二者全部差异归因于缓存或调度。
- 数据代表当前转接板连接；链路仍有已知可纠正错误。此处不推断更换转接板后的额外收益。
- 没有采集逐请求块层提交/完成 trace，无法证明每个短时突发的设备内部饱和程度；吞吐、回放和整盘采样足以说明当前推理未持续用尽带宽。
