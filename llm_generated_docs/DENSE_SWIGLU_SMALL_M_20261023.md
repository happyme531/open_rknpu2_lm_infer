# Dense W4A8 新版 SwiGLU 的小 M 实验，2026-10-23

## 结论

对这组 Qwen3-4B layer2/H2560/F9728 原始权重和真实输入，固定 `rows<32` 拒绝融合已经偏保守。新版四线程融合在 M1/2/4/8/16/31 的完整 FFN 均值分别快 2.10%/3.04%/4.40%/7.27%/14.87%/25.70%。M1 的绝对收益约 32 μs，较小；短 prefill 的收益更明显。

不能只删除 M 门槛然后原样使用普通 GEMM 的线程策略。普通 tuner 为 M2/4/8 gate/up 选了单线程；M8 沿用单线程融合反而慢 0.57%，换四线程融合则快 7.27%。应以包含激活的完整调用选择线程/执行策略。

本轮只有算子库目录中的纯 C++ 实验和 Python 编排/汇总，没有修改生产源码、runtime 条件或提交代码。结果不是整模型吞吐或 PPL 结果。

### 旧版对照的实现边界

全部探针使用 C++。独立 FP64 激活复刻 `src/model/cpu.rs` 的 degree12 FP64 NEON exp、±80 范围分支和 FP32 SwiGLU 算术；两种独立激活统一使用 OpenMP4、256 元素分块，≤1024 元素时串行。新版 FP32 直接复用算子库的同一份 degree7 SIMD 内核。

它是相同数学和分块的 C++ 对照，不是 Rust/Rayon 调用时间的逐指令重放；小到十几微秒的收益仍需在实际 runtime 接入时复核。曾准备复用 Rust CPU 函数的方案已删除，没有构建或使用 Rust shim。

## 六种路径

| 标识 | 路径 |
|---|---|
| split_fp64 | 已调优普通 gate/up → 独立旧 FP64 SwiGLU → 已调优普通 Down |
| split_fp32 | 相同 gate/up/Down，只换独立新版 FP32 SwiGLU |
| fused_1t | 新版 gate/up+SwiGLU 融合，gate/up workspace CPU1 → 普通 Down |
| fused_4t | 新版 gate/up+SwiGLU 融合，gate/up workspace CPU4 → 普通 Down |
| ffn_1t | 完整 FFN 接口，gate/up CPU1，并让 Down 复用行 scale |
| ffn_4t | 完整 FFN 接口，gate/up CPU4，并让 Down 复用行 scale |

每个 M 的所有模式固定相同 K/M/N 分块、输入布局、pipeline、NPU cores 和 Down 策略。单/四线程变量改变 gate/up workspace 的全部 CPU 工作，不只是激活线程数。Down 的线程数始终使用选中的普通 GEMM 策略。

当前 runtime 分流的 C++ 等价基线：M<32 使用 split_fp64；本次 M≥32 的 gate/up 都选择 CPU4/CPU reduce，因此基线是 fused_4t。

## 阶段解释

- M1：独立激活 FP64→FP32 从 41.96→27.77 μs，但完整 FFN 只快 0.85%。四线程融合的 gate/up 含激活为 971.21 μs，独立路径 gate/up+旧激活为 959.47+41.96 μs；所以完整收益约 32 μs。Down 约 499 μs，基本不变。
- M8：普通 gate/up 的 CPU1/chain 策略不适合直接套给融合工作。四线程融合增加部分扫描/打包的线程开销，但 CPU 归约/收尾从约 170.29 降到 133.96 μs，并消除独立旧激活的 162.09 μs 区间；完整调用仍明显更快。
- M31：独立旧激活约 1084.04 μs，新版独立激活约 354.63 μs。融合还省去完整 gate/up 输出和中间 accumulator 的访问，这使其优于只替换激活算法。
- 完整 FFN 的 `down.activation_scan_us=0`，但收集/归并 maxabs、缓存状态变化等成本仍在总调用中；M32 的近零增量说明不能只把被删除的扫描时间算成收益。

### Driver 诊断

独立诊断批次每种模式每个 M 仅 4 次调用，用于确认提交和设备区间，不代替上面 96 次调用的正式统计。M8 是比较清楚的一例：

| M8 路径 | 完整调用 μs | driver 硬件区间 μs | ioctl 墙钟 μs | submits | GEMM tasks |

| split FP64 | 1994.869 | 1367.052 | 1395.198 | 2 | 30 |

| FFN CPU4 | 1822.420 | 1366.031 | 1396.146 | 2 | 30 |

提交/任务数不变，设备区间基本相同，收益来自 CPU 处理与衔接。M1 的 driver 硬件区间约 1.3 ms，解释了为何完整 1.5 ms 调用只从激活优化获得几十微秒。

驱动的 `hw_elapse_time` 实际为 ns（库的 `hardware_ns` 接口直接返回此字段）；汇总时除以 1000。初次诊断 CSV 的该列误命名为 us，已仅将列名纠正为 `driver_hw_ns`，原始字节保留在 `diagnostic/raw/`。正式采样关闭该诊断，不受此列名修正影响。硬件区间包含设备/内存等待，不代表纯 MAC 时间。

## 正确性与边界

- 两个正式进程合计 360 组比较：每个 M 的原输入、全零、4 倍、取负，五条候选分别对旧独立 FP64 路径比较。
- 最大 middle relative L2：`3.39997845e-8`；最大最终输出 relative L2：`1.12736703e-8`；最终输出最大绝对差：`5.96046448e-8`。
- 每个计时调用输出与本模式首次输出逐位一致，gate/up、middle、output 的保护区均通过。
- 初测、正式与诊断 runner 均 exit0，`restore_errors=[]`。
- 这是一个真实层的宽 FFN，不外推到 F512 等小中间宽度。没有测全模型 PPL，也没有修改模型当前的融合条件。

## 后续建议

1. 这组形状支持新版四线程融合覆盖 M1–31，不应继续把 M32 当成已证明最优的分界。M1 收益小，可以单独做 runtime 接入复核。
2. 去掉小 M 禁用条件时，必须同时处理普通 GEMM tuner 为 M2/4/8 选单线程的问题。更稳妥的是让融合调用使用自身策略，而非全局将普通 Linear 改成四线程。
3. FP32 激活可以独立迁移，但其收益小于完整融合。完整 FFN/scale 复用可随后接入，M32 等增量接近零的点不要宣称普遍加速。

## 补充：CPU 总消耗与平均占用

用户询问增加融合线程是否会显著增加 CPU 占用，因此另跑相同形状/权重的 CPU 成本测量。使用 `CLOCK_PROCESS_CPUTIME_ID`，累计进程所有线程的 user+system CPU 时间；阻塞等待 NPU 的时间不计为 CPU 工作。每个区间连续调用 8 次，在区间外检查输出、保护区和写 CSV，以摊薄 CPU clock 采样开销。

两个进程，每个 M/模式每进程 12 个正反轮转周期，每个模式每周期 2 个区间。合计每个 M/模式 384 次调用、48 个测量区间、24 个配对周期。仍为四大核 mask0xf0、CPU 2.256 GHz、NPU 1 GHz、OpenMP PASSIVE/GOMP_SPINCOUNT=0。CPU 成本与 wall time 都采用这次独立批次，不与前面逐调用采样的时间拼接。

### 小 M：旧独立 FP64 → 新四线程融合

本批所有小 M 的四线程融合均降低 CPU 总消耗和平均占用，不是通过大幅增加 CPU 消耗换时延。旧独立 SwiGLU 本来就会使用四线程；新路径减少 FP64 计算和中间数据处理，并延长部分归约/打包阶段的并行区间。瞬时仍可能四核一起工作，本实验没有采样瞬时逐核峰值或整板功耗。
